# 需求文档

## 简介

本文档定义了将贪心调度算法从按天分割处理改造为全局多天处理的需求。当前系统按天独立处理排班，每天重新初始化可行性张量和回溯引擎，导致跨日约束被割裂、回溯无法跨日、MRV全局最优性被破坏。通过实现全局多天调度，系统可以正确处理跨日约束（如时段11到时段0的连续性）、支持跨日回溯、实现真正的全局MRV优化，从而显著提高排班质量和完整性。

## 术语表

- **全局调度 (Global Scheduling)**: 一次性处理所有天数的排班，而非按天分割处理
- **全局时段索引 (Global Period Index)**: 跨越所有天数的连续时段索引，范围为 0 到 (总天数 × 12 - 1)
- **局部时段索引 (Local Period Index)**: 单天内的时段索引，范围为 0 到 11
- **跨日约束 (Cross-Day Constraints)**: 涉及相邻天数时段的约束，如时段11（22:00-00:00）和次日时段0（00:00-02:00）的连续性
- **全局可行性张量 (Global Feasibility Tensor)**: 维度为 [哨位数, 总天数×12, 人员数] 的三维张量
- **全局MRV (Global MRV)**: 在所有天数的所有时段中选择候选人员最少的哨位-时段组合
- **跨日回溯 (Cross-Day Backtracking)**: 回溯引擎可以撤销前一天的分配决策
- **时段映射 (Period Mapping)**: 全局时段索引与（日期索引，局部时段索引）之间的转换
- **内存优化 (Memory Optimization)**: 在保证功能的前提下减少全局张量的内存占用
- **增量初始化 (Incremental Initialization)**: 分批初始化张量以避免启动时的长时间等待

## 需求

### 需求 1

**用户故事:** 作为系统管理员，我希望排班算法能够正确处理跨日约束，以便确保相邻天数时段之间的人员分配符合休息时间等约束。

#### 验收标准

1. WHEN 系统分配时段11（22:00-00:00）的人员 THEN 系统应考虑次日时段0（00:00-02:00）的约束影响
2. WHEN 系统分配次日时段0的人员 THEN 系统应考虑前一天时段11的已有分配
3. WHEN 人员在时段11被分配 THEN 系统应在可行性张量中标记该人员在次日时段0-2不可用（休息约束）
4. WHEN 系统验证连续工作约束 THEN 系统应将时段11和次日时段0视为连续时段
5. WHEN 系统计算夜哨唯一约束 THEN 系统应将当天时段11和次日时段0-2识别为跨日的夜哨周期

### 需求 2

**用户故事:** 作为系统管理员，我希望回溯机制能够跨越天数边界，以便在后续天数遇到死胡同时可以回溯到前一天的决策点。

#### 验收标准

1. WHEN 系统在第N天遇到无解情况 THEN 系统应能够回溯到第N-1天的分配决策
2. WHEN 系统回溯到前一天 THEN 系统应正确恢复前一天的可行性张量状态
3. WHEN 系统跨日回溯 THEN 系统应保持分配栈的连续性，不因天数边界而中断
4. WHEN 回溯深度超过单天的分配数量 THEN 系统应继续回溯到更早的天数
5. WHEN 系统完成跨日回溯 THEN 系统应重新评估所有受影响天数的分配方案

### 需求 3

**用户故事:** 作为系统管理员，我希望MRV策略能够在全局范围内选择最优的哨位-时段组合，以便提高排班算法的整体效率。

#### 验收标准

1. WHEN 系统执行MRV选择 THEN 系统应在所有天数的所有时段中寻找候选人员最少的位置
2. WHEN 第1天的某个时段和第3天的某个时段候选人员数量相同 THEN 系统应根据统一的优先级规则选择
3. WHEN 系统更新候选人员计数 THEN 系统应同时更新所有受影响天数的计数
4. WHEN 系统分配一个时段 THEN 系统应更新全局范围内所有受影响时段的候选人员计数
5. WHEN MRV策略选择下一个时段 THEN 系统应返回全局时段索引而非局部时段索引

### 需求 4

**用户故事:** 作为开发人员，我希望系统能够高效地管理全局可行性张量，以便在合理的内存占用下支持多天排班。

#### 验收标准

1. WHEN 系统初始化全局张量 THEN 系统应使用维度为 [哨位数, 总天数×12, 人员数] 的三维结构
2. WHEN 总天数为8天 THEN 系统应创建时段维度为96（8×12）的全局张量，其中时段索引0-11对应第1天，12-23对应第2天，以此类推
3. WHEN 系统访问张量元素 THEN 系统应使用位运算优化存储和访问效率
4. WHEN 内存占用超过阈值 THEN 系统应提供降级方案（如分段处理）
5. WHEN 系统释放资源 THEN 系统应正确释放全局张量占用的内存

### 需求 5

**用户故事:** 作为系统管理员，我希望系统能够将全局时段索引正确映射到具体的日期和时段，以便在结果中准确显示分配信息。

#### 验收标准

1. WHEN 系统使用全局时段索引 THEN 系统应能够计算对应的日期索引和局部时段索引
2. WHEN 全局时段索引为13 THEN 系统应映射为第2天（索引1）的时段1
3. WHEN 系统保存排班结果 THEN 系统应将全局时段索引转换为日期和时段的组合
4. WHEN 系统显示排班结果 THEN 系统应使用日期和时段的可读格式
5. WHEN 系统处理手动指定 THEN 系统应正确转换用户输入的日期时段到全局索引

### 需求 6

**用户故事:** 作为系统管理员，我希望全局调度算法的性能在可接受范围内，以便不影响用户体验。

#### 验收标准

1. WHEN 系统初始化全局张量 THEN 系统应在5秒内完成初始化（8天×20哨位×50人员）
2. WHEN 系统执行全局MRV选择 THEN 系统应在100毫秒内完成单次选择
3. WHEN 系统执行完整排班 THEN 系统应在原按天处理时间的1.5倍内完成
4. WHEN 系统执行跨日回溯 THEN 系统应使用增量状态恢复而非完全重建
5. WHEN 系统报告进度 THEN 系统应基于全局时段总数计算进度百分比

### 需求 7

**用户故事:** 作为开发人员，我希望全局调度架构能够与现有的约束验证和评分系统兼容，以便最小化代码改动。

#### 验收标准

1. WHEN 系统验证硬约束 THEN 系统应使用现有的约束验证器接口
2. WHEN 系统计算软约束评分 THEN 系统应使用现有的评分计算器
3. WHEN 系统应用夜哨唯一约束 THEN 系统应正确识别跨日的夜哨周期（时段11, 0, 1, 2）
4. WHEN 系统应用休息时间约束 THEN 系统应正确计算跨日的连续工作时长
5. WHEN 系统集成全局调度 THEN 系统应保持现有约束逻辑的语义不变

### 需求 8

**用户故事:** 作为系统管理员，我希望在排班过程中能够看到全局调度的执行情况，以便了解算法的运行状态。

#### 验收标准

1. WHEN 系统开始全局调度 THEN 系统应报告总时段数和预计完成时间
2. WHEN 系统完成每个时段的分配 THEN 系统应更新进度百分比（已分配时段数/总时段数）
3. WHEN 系统执行跨日回溯 THEN 系统应在进度报告中标注回溯事件
4. WHEN 系统完成排班 THEN 系统应报告总分配数、回溯次数、跨日回溯次数
5. WHEN 系统遇到性能问题 THEN 系统应在日志中记录关键性能指标

### 需求 9

**用户故事:** 作为开发人员，我希望系统能够提供配置选项在全局调度和按天调度之间切换，以便在过渡期间保持向后兼容。

#### 验收标准

1. WHEN 系统初始化调度器 THEN 系统应允许配置是否启用全局调度模式
2. WHEN 全局调度模式被禁用 THEN 系统应使用原有的按天处理逻辑
3. WHEN 全局调度模式被启用 THEN 系统应使用新的全局处理逻辑
4. WHEN 配置参数无效 THEN 系统应使用默认值（启用全局调度）并记录警告
5. WHEN 系统切换调度模式 THEN 系统应在日志中记录当前使用的模式

### 需求 10

**用户故事:** 作为测试人员，我希望能够验证全局调度的正确性，以便确保跨日约束和回溯机制正常工作。

#### 验收标准

1. WHEN 系统完成全局排班 THEN 系统应验证所有跨日约束都得到满足
2. WHEN 系统执行跨日回溯 THEN 系统应验证回溯后的状态一致性
3. WHEN 系统处理边界情况 THEN 系统应正确处理第一天的时段0和最后一天的时段11
4. WHEN 测试全局调度 THEN 系统应提供测试用例覆盖跨日约束、跨日回溯、全局MRV等场景
5. WHEN 系统报告诊断信息 THEN 系统应包含全局时段索引、日期映射、跨日约束违反等详细信息

### 需求 11

**用户故事:** 作为系统管理员，我希望系统能够优雅地处理大规模排班场景，以便支持更长时间跨度的排班需求。

#### 验收标准

1. WHEN 排班天数超过配置的阈值（默认30天） THEN 系统应提供分段处理选项以控制内存占用
2. WHEN 系统使用分段处理 THEN 系统应在段边界处保持跨日约束的正确性
3. WHEN 系统检测到内存占用超过配置的阈值 THEN 系统应自动降级到按天处理模式并通知用户
4. WHEN 系统处理大规模排班 THEN 系统应提供取消操作的能力
5. WHEN 系统完成大规模排班 THEN 系统应在结果中标注使用的处理模式（全局、分段或按天）

### 需求 12

**用户故事:** 作为开发人员，我希望全局调度的代码结构清晰易维护，以便后续的功能扩展和问题修复。

#### 验收标准

1. WHEN 系统实现全局调度 THEN 系统应将时段映射逻辑封装为独立的工具类
2. WHEN 系统实现全局调度 THEN 系统应将全局张量管理封装为独立的组件
3. WHEN 系统实现全局调度 THEN 系统应保持MRV策略、回溯引擎、约束验证器的接口稳定
4. WHEN 系统修改全局调度逻辑 THEN 系统应不影响其他调度模式（如遗传算法）
5. WHEN 系统添加新约束 THEN 系统应能够无缝集成到全局调度框架中
